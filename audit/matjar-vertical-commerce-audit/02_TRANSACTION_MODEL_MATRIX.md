# 02 — مصفوفة نماذج التعامل (Transaction Model Matrix)

> النماذج A–L من مواصفة التدقيق. العمود «الحالي» مستخرَج من `categoryModule.kind` + سطح صفحة المتجر الفعلي (`store/[id]/page.tsx`). «المطلوب» = النموذج الصحيح مهنيًّا.

## أ. تعريف النماذج ووجودها في مطجر اليوم

| # | النموذج | موجود في مطجر؟ | الآليّة الحاليّة |
|---|---|---|---|
| A | شراء منتج مباشر (Direct purchase) | ✅ ناضج | `orders` + `order_items` + سلّة + delivery zones (0172) |
| B | طلب طعام (Food order) | ✅ لكنه = A | نفس تدفّق A؛ ينقصه modifiers إلزاميّة + مجدوَل + إتاحة صنف |
| C | حجز موعد (Appointment) | ✅ ناضج نسبيًّا | `bookings` + doctor picker + slots + allocation_mode (0174) |
| D | حجز إقامة (Accommodation) | ❌ **غائب** | يُحشَر في C (فترة مفردة) — لا مدى تواريخ/ليالٍ/ضيوف/سعر لليلة |
| E | حجز طاولة (Table reservation) | ✅ | `reservations` منفصل عن الطلب (task #13) |
| F | طلب خدمة (Service request) | ⚠️ جزئي | `service_requests` (وصف+هاتف+عنوان)، بلا صور/إلحاح/إسناد/تتبّع |
| G | طلب عرض سعر (Quotation) | ⚠️ جزئي | `service_requests.quote_amount/quote_note` موجود؛ بلا brief منظّم |
| H | استفسار/lead (Lead) | ❌ **غائب** | لا جدول leads؛ العقار/السيّارة بلا التقاط lead |
| I | إعلان عقاري (Property listing) | ⚠️ خصائص فقط | `products.attributes`؛ بلا تدفّق معاينة/وكيل/خريطة بحث |
| J | إعلان مركبة (Vehicle listing) | ❌ خاطئ | يُعامَل كـ commerce (سلّة) — يجب lead/listing |
| K | تذكرة/فعاليّة (Ticket/event) | ❌ غائب | لا نوع تذكرة/كميّة/بيانات حاضر |
| L | اشتراك/عضويّة (Membership) | ❌ معلَن فقط | وحدة `memberships` بلا شراء اشتراك حقيقي |

**الخلاصة الصادمة:** من 12 نموذجًا، **3 ناضجة (A, C, E)**، **3 جزئيّة (B, F, G)**، **6 غائبة أو خاطئة (D, H, I, J, K, L)**. مطجر يغطّي التجارة والمواعيد جيّدًا، ويفشل في **الإقامة، القوائد (leads)، التأجير، التذاكر، والعضويّات** — وهي جوهر 5 من قطاعاته الـ17.

## ج. تجميع النماذج → أولويّة البناء

**النماذج التي تحتاج بناء جديد (مرتّبة بالأثر):**
1. **Model D — الإقامة/التأجير بمدى تواريخ** (hospitality + automotive rentals + events venues). أعلى أثر: يفتح قطاعين حرِجين. الأساس التقني الواحد (calendar + date-range + per-period pricing + availability blocking) يُعاد استخدامه.
2. **Model H — Leads/Inquiries** (realEstate + automotive + professional + high-value). جدول `leads` واحد + نموذج تواصل/معاينة قابل لإعادة الاستخدام يصلح 4 قطاعات.
3. **Model L + courses/classes — العضويّات والتسجيل** (fitness + education). شراء اشتراك + جدول حصص/دورات بسعة.
4. **Model K — التذاكر** (events). نوع تذكرة + كميّة + بيانات حاضر.
5. **إتمام Model B/F/G** — modifiers الطعام، brief الخدمات، إصلاح drift نموذج الطلب.

**القطاعات التي تستطيع بأمان استخدام تدفّق A/C المشترك دون تغيير جوهري:** retail، healthcare، beauty، petCare، food(delivery فقط). هذه لا تُلمَس.

## د. الاكتشاف البنيوي الحاسم (من تدقيق صفحة المتجر)

المشكلة ليست فقط «تدفّق واحد للجميع»، بل **نظاما تحكّم متعارضان**:
- **سِجِلّ الوحدات** (`resolveStoreModules`) يقرّر ما يُعرَض لبعض الأقسام.
- **شروط مبرمَجة يدويًّا** (`bookingCategories = {services, healthcare, realEstate}`، فحوص `category === …`) تقرّر أقسامًا أخرى.

النتيجة: قطاعات تُعلن وحدة `requests` في السِجِلّ لكن **لا يظهر لها نموذج طلب** على الصفحة العامّة (professional, contractors, realEstate, automotive) — لأن `ServiceRequestForm` مربوط يدويًّا بـ`services`/`healthcare` فقط. أي **إصلاح محرّك القطاعات يجب أن يوحّد المصدر: كل ما تُعرَضه الصفحة يُشتَقّ من الوحدات المُفعَّلة، لا من قوائم مبرمَجة**. (انظر 17_DYNAMIC_CATEGORY_ENGINE.)
