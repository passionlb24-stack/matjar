# تدقيق قطاعَي البقالة/المزارع والصيدليّات/المختبرات — مطجر

> يعالج هذا الملف قطبين تجاريّين (kind=commerce) لهما احتياجات جوهريّة مختلفة عن retail العام:
> 1. **مزارع ومنتجات محلّية + السوبرماركت/البقالة** (slug: `farm` + استخدام retail للبقالة) — Grocery
> 2. **صيدليّات ومختبرات** (slug: `pharmacy`) — Pharmacy + Labs
>
> **أخطر اكتشافين:** (أ) البقالة/المزارع **بلا تسعير بالوزن/الوحدة** إطلاقًا (لا per_kg، لا unit_type)، بلا نوافذ توصيل مجدولة، بلا بدائل. (ب) قطاع `pharmacy` **يخلط الصيدليّة (بيع OTC، نموذج A) بالمختبرات (حجز فحص/عيّنة منزليّة، نموذج C) في قطاع commerce واحد** — يجب فصلهما؛ ولا رفع وصفة، لا تعامل مع أصناف خاضعة للرقابة، لا تنويه امتثال قانوني.

# القسم الأوّل: البقالة والمزارع (Grocery / Farm)

## A. تعريف القطاع

- **الاسم:** مزارع ومنتجات محلّية — Farm & Local Produce (slug: `farm`, kind: commerce, itemsKey: products). والبقالات/السوبرماركت عمليًّا تحت `retail`/`food` أو `farm`.
- **الأعمال المستهدفة:** مزارع تبيع خضارًا/فواكه/بيضًا/ألبانًا/عسلًا/زيت زيتون مباشرة، محلّات المونة والمؤن، الجزارات، السوبرماركت والدكاكين، محلّات الأجبان والمخبوزات المحلّية.
- **هدف العميل:** يطلب سلّة أسبوعيّة/يوميّة من مواد طازجة، يعرف السعر بالكيلو/الوحدة بدقّة، يستلم في نافذة زمنيّة مناسبة، ويثق بالطزاجة والمصدر.
- **هدف التاجر:** يعرض منتجات تُباع بالوزن/الوحدة، يدير طلبات متكرّرة، ينظّم توصيلًا مجدولًا (لا فوري بالضرورة)، ويتعامل مع نفاد/بدائل مادّة طازجة.

## B. نموذج التعامل الصحيح

**النموذج A (الشراء المباشر) — صحيح**، لكن يحتاج ثلاث امتدادات حرجة لا يملكها مطجر:
1. **تسعير بالوزن/الوحدة** (per_kg / per_unit / per_bunch) بدل سعر ثابت للقطعة.
2. **نوافذ توصيل مجدولة** (اختَر يوم/فترة) بدل توصيل «الآن» فقط.
3. **بدائل عند النفاد** (substitutions) — «إن نفد، استبدل بـ… / اتّصل بي / احذف».

## C. تجربة مطجر الحاليّة (من الأدلّة)

**الشكل الحالي:** commerce → شبكة منتجات + سلّة + `place_order` COD + مناطق توصيل (0172: fee/min_order/free_over/eta). يعمل كبقالة بدائيّة.

**المشاكل الموثّقة:**
1. **لا تسعير بالوزن.** `products.price` رقم ثابت للقطعة فقط؛ لا `unit_type` ولا `price_per_kg`. بيع «كيلو بندورة» أو «ربطة نعنع» أو «نصف كيلو لحمة» مستحيل التعبير عنه بدقّة → التاجر يزوّر (يسجّل «قطعة») أو يستعمل واتساب.
2. **لا نوافذ توصيل مجدولة.** `orders` بلا `scheduled_for`. `store_delivery_zones` تعطي eta_min/max فقط (توصيل فوري)؛ لا اختيار «غدًا صباحًا 8–11». الطزاجة تتطلّب جدولة.
3. **لا بدائل.** لا حقل substitution preference على order_item؛ إن نفد صنف طازج، لا مسار سوى الإلغاء أو اتّصال يدوي.
4. **لا طلب متكرّر / سلّة محفوظة** (reorder) — أساس البقالة.
5. **المخزون عدد صحيح فقط** (stock int) — لا يعبّر عن «7.5 كغ متبقّية».

## D. onboarding التاجر المثالي

الحالي: شاشة عامّة بلا حقول قطاع. **المطلوب:**
- **نوع البيع الافتراضي** (بالقطعة / بالوزن) → يفعّل حقول الوحدة على المنتجات.
- **جدول التوصيل** (أيّام + نوافذ زمنيّة متاحة، حد أدنى للطلب، رسوم) → يفعّل نوافذ مجدولة.
- **سياسة البدائل الافتراضيّة** (استبدال تلقائي / اتّصال / حذف).
- checklist: منتجات بأسعار وحدة + نافذة توصيل واحدة + حد أدنى للطلب.

## E. نموذج المنتج المثالي

- name/name_en, gallery, section, **unit_type** (قطعة/كغ/غرام/ربطة/علبة/لتر — مطلوب), **price_per_unit** (مطلوب), **step** (خطوة الطلب: 0.25 كغ مثلًا), stock عشري, **origin/source** (محلّي/مزرعة فلان — عامل ثقة), **perishable** (boolean → يفعّل جدولة/بدائل), **organic** (اختياري فلتر), تاريخ صلاحيّة/طزاجة (اختياري).
- **بدائل مقترحة** لكل منتج (عند النفاد).

## F. صفحة تفاصيل العميل المثاليّة

معرض صور → الاسم → **السعر بالوحدة (/كغ)** بوضوح + منتقي الكميّة بالخطوة (0.5 كغ…) → المصدر/الطزاجة → توفّر + **نافذة التوصيل التالية** → CTA أضف للسلّة → **تفضيل البديل** («إن نفد: استبدل/اتّصل/احذف») → منتجات ذات صلة/سلّة سابقة.

## G. تدفّق التعامل المثالي

تصفّح → إضافة بالوزن/الوحدة → سلّة (حد أدنى) → **اختيار نافذة توصيل** → تفضيل بدائل → checkout COD → تجهيز (وزن فعلي قد يعدّل السعر — يحتاج تأكيد) → توصيل مجدول → إعادة طلب بضغطة.

## H. لوحة تحكّم التاجر

- منتجات بوحدات وأسعار/كغ + مخزون عشري + تنبيه نفاد.
- **مدير نوافذ التوصيل** (سعات لكل نافذة).
- طابور طلبات مع بدائل مقترحة عند النفاد.
- inventory (business tier) للسوبرماركت.

## I. مسار الحالة

orders.status كافٍ، **ناقص:** حالة «بانتظار تأكيد الوزن/السعر النهائي» (طازج يُوزن عند التجهيز)، وحالة «بديل مقترح — بانتظار موافقة العميل».

## J. الإشعارات

عميل: تأكيد + نافذة التوصيل + **«صنف نفد — نقترح بديلًا، وافق؟»** + تعديل السعر بعد الوزن. تاجر: طلب جديد + نفاد صنف طازج. 

## K. الثقة والأمان

مصدر المنتج/الطزاجة، صور واقعيّة، verification للمزارع، مراجعات، شفافيّة تعديل السعر بعد الوزن (لا مفاجآت).

## L. مقارنة المنافسين

- **Instacart / Talabat Mart / Carrefour Now:** تسعير بالوزن + نوافذ تو(صيل مجدولة + بدائل ذكيّة + reorder + استبدال بموافقة عبر الرسائل → مطجر يفتقد الثلاثة.
- **تعديل لبناني:** COD صحيح، USD/LBP، واتساب للتنسيق، المزارع المحلّية = ميزة تمايز (المصدر/الطزاجة)، جدولة مهمّة لتفادي فساد الطازج.

## M. تحليل الفجوات (Grocery)

- **Critical — لا تسعير بالوزن/الوحدة** (لا unit_type/price_per_kg/step، stock int). يمنع البيع الدقيق لكل الطازج.
- **Critical — لا نوافذ توصيل مجدولة** (لا orders.scheduled_for).
- **High — لا بدائل عند النفاد.**
- **High — لا reorder / سلّة محفوظة.**
- **Medium — لا مخزون عشري.**
- **Medium — لا حقل مصدر/طزاجة/صلاحيّة.**
- **Low — لا فلتر عضوي/محلّي.**

## N. توصية المنتج (Grocery)

**MVP:** unit_type + price_per_unit + step + مخزون عشري؛ نوافذ توصيل مجدولة (scheduled_for + مدير نوافذ). **Phase 2:** بدائل بموافقة + reorder + تأكيد وزن/سعر نهائي. **Phase 3:** حقل مصدر/طزاجة + فلاتر عضوي/محلّي + اشتراك سلّة أسبوعيّة.

# القسم الثاني: الصيدليّات والمختبرات (Pharmacy / Labs)

## A. تعريف القطاع

- **الاسم:** صيدليّات ومختبرات — Pharmacy & Labs (slug: `pharmacy`, kind: commerce حاليًّا).
- **الأعمال المستهدفة:** الصيدليّات (بيع أدوية OTC، مستحضرات، مستلزمات)، **والمختبرات الطبّية** (فحوصات دم/تحاليل، عيّنات منزليّة، حزم فحص).
- **هدف العميل (صيدليّة):** يشتري دواءً/مستلزمًا، أحيانًا بوصفة. **(مختبر):** يحجز فحصًا، ربّما بزيارة منزليّة، يستلم النتيجة.
- **هدف التاجر (صيدليّة):** بيع OTC نقدًا، والتعامل مع الوصفات. **(مختبر):** جدولة فحوصات وعيّنات وتسليم نتائج.

## B. نموذج التعامل الصحيح — **قطاعان لا قطاع واحد**

- **الصيدليّة = نموذج A** (شراء مباشر COD) + طبقة **رفع وصفة** + تنويه امتثال.
- **المختبر = نموذج C** (حجز موعد/عيّنة منزليّة) — كتالوج فحوصات + حزم + صيام + زيارة منزليّة + فرع + سلوت + تسليم نتيجة.

**الخطأ الحالي:** الاثنان محشوران في قطاع commerce واحد `pharmacy` → المختبر يُعامَل كبيع منتجات بالسلّة، وهو خطأ نموذجيّ (كما automotive=commerce الخاطئ). يجب فصل `labs` عن `pharmacy`، أو على الأقل تشغيل محرّك الحجز (BookingPanel/place_booking) للمختبر.

## C. تجربة مطجر الحاليّة (من الأدلّة)

- `pharmacy` = kind commerce → شبكة منتجات + سلّة + COD. مناسب جزئيًّا للصيدليّة، **خاطئ كليًّا للمختبر**.
- **محرّك الحجز الجيّد (place_booking 0174) مقيّد لـ {services, healthcare, realEstate} فقط** — المختبر ليس ضمنها، فلا يحصل على حجز رغم أنّه يحتاجه. حتّى لو صُنّف healthcare، يخلط مع العيادات.
- **لا رفع وصفة** (لا حقل prescription upload على المنتج/الطلب؛ custom_fields jsonb موجود على orders لكن بلا مسار مخصّص).
- **لا تعامل مع أصناف خاضعة للرقابة** (لا علامة controlled، لا منع بيع بلا وصفة).
- **لا تنويه امتثال/إخلاء مسؤوليّة طبّي.**

## D. onboarding التاجر المثالي

- **اختيار نوع العمل: صيدليّة أو مختبر** (يقرّر نموذج التعامل).
- صيدليّة: تفعيل رفع الوصفة (اختياري/إلزامي لأصناف)، تنويه امتثال، ساعات.
- مختبر: كتالوج فحوصات، حزم، تفعيل زيارة منزليّة + رسومها، فروع، ساعات/سلوتات، طريقة تسليم النتيجة.

## E. نموذج المنتج/الخدمة المثالي

**صيدليّة (منتج):** name, category (دواء/مكمّل/عناية/مستلزم), price, **requires_prescription** (boolean — يمنع الإتمام بلا رفع وصفة), **controlled** (خاضع للرقابة — علامة/منع), الشركة المصنّعة, الجرعة/العبوة, صورة, مخزون. تنويه: «استشر طبيبك/الصيدلي».

**مختبر (فحص كخدمة):** name (CBC، سكّر…), **price**, **fasting_required** (صيام — boolean حرج), **sample_type** (دم/بول…), **turnaround** (مدّة النتيجة), **home_visit** (متاح + رسوم), **package** (حزمة فحوصات مجمّعة بسعر), فرع, **سلوت موعد** (place_booking). النتيجة: طريقة التسليم (استلام/رفع رقمي).

## F. صفحة تفاصيل العميل المثاليّة

- **صيدليّة:** صورة/اسم/سعر → **«يتطلّب وصفة»** بوضوح إن لزم → **رفع الوصفة** قبل الإضافة للسلّة → تنويه استشارة → CTA أضف للسلّة → COD.
- **مختبر:** اسم الفحص/السعر → **«يتطلّب صيام N ساعة»** بارز → نوع العيّنة/مدّة النتيجة → **زيارة منزليّة (+رسوم) أو حضور للفرع** → منتقي سلوت الموعد → CTA «احجز الفحص» → تنويه/سياسة.

## G. تدفّق التعامل المثالي

- **صيدليّة:** تصفّح → (إن وصفة: رفعها) → سلّة → checkout COD → تجهيز → توصيل/استلام.
- **مختبر:** تصفّح فحوصات/حزم → اختيار زيارة منزليّة أو فرع → اختيار سلوت + تنبيه صيام → تأكيد الحجز (place_booking) → أخذ العيّنة → إشعار «النتيجة جاهزة» → تسليم النتيجة.

## H. لوحة تحكّم التاجر

- **صيدليّة:** كتالوج + علامة وصفة/رقابة + طابور طلبات + مراجعة الوصفات المرفوعة.
- **مختبر:** كتالوج فحوصات/حزم + مدير سلوتات وزيارات منزليّة (provider_availability موجود ✅) + طابور حجوزات + **رفع/تسليم النتائج**.

## I. مسار الحالة

- صيدليّة: orders.status + حالة «بانتظار مراجعة الوصفة» (مفقودة).
- مختبر: bookings.status (pending→accepted→scheduled→completed) ✅ + حالة «العيّنة مأخوذة» و«النتيجة جاهزة/مُسلّمة» (مفقودة).

## J. الإشعارات

- صيدليّة: تأكيد، «وصفتك قيد المراجعة/مقبولة/مرفوضة»، خروج للتوصيل.
- مختبر: تأكيد الحجز، **تذكير الصيام قبل الموعد**، «العيّنة مأخوذة»، **«نتيجتك جاهزة»**.

## K. الثقة والأمان — الأعلى حساسيّة في المنصّة

- **امتثال قانوني:** بيع الأدوية الموصوفة يتطلّب وصفة؛ الأصناف الخاضعة للرقابة ممنوعة دون ضوابط — مطجر بلا أي من ذلك اليوم = خطر قانوني.
- **إخلاء مسؤوليّة طبّي** إلزامي («ليست استشارة طبّية، استشر مختصًّا»).
- **خصوصيّة النتائج المخبريّة** (بيانات صحّية حسّاسة — يجب حماية رفع/تسليم النتائج، لا تمريرها في URL — يتّسق مع قواعد الخصوصيّة).
- **verification** ترخيص الصيدليّة/المختبر (store_verifications: kind/issuer/number/expires — موجود ✅، يجب إلزامه هنا).
- **(للتحقّق)** القوانين اللبنانيّة لبيع الأدوية أونلاين خارج نطاق هذا التدقيق التقني — يجب مراجعة قانونيّة قبل الإطلاق.

## L. مقارنة المنافسين

- **صيدليّات أونلاين (مثل Noon/أمازون فارماسي، للتحقّق تفاصيلها):** رفع وصفة إلزامي للموصوف، فصل OTC عن الموصوف، تنويهات، تحقّق صيدلي.
- **مختبرات (مثل نماذج booking صحّي):** كتالوج فحوصات + حزم + صيام + عيّنة منزليّة + تسليم نتيجة رقمي.
- **تعديل لبناني:** COD، واتساب، الزيارة المنزليّة شائعة ومطلوبة، الترخيص وثقة الصيدلي حاسمة.

## M. تحليل الفجوات (Pharmacy/Labs)

- **Critical — دمج الصيدليّة والمختبر في قطاع commerce واحد.** المختبر يحتاج حجز (C) لا سلّة (A). يجب فصل labs أو توسيع بوّابة الحجز إليه.
- **Critical — لا رفع وصفة ولا تعامل مع أصناف خاضعة للرقابة** = خطر امتثال قانوني.
- **Critical — لا تنويه/إخلاء مسؤوليّة طبّي.**
- **High — المختبر بلا كتالوج فحوصات/حزم/صيام/زيارة منزليّة/تسليم نتيجة.**
- **High — لا حالات «مراجعة وصفة» و«النتيجة جاهزة».**
- **Medium — خصوصيّة/حماية رفع وتسليم النتائج المخبريّة.**
- **Medium — إلزام verification الترخيص لهذا القطاع.**

## N. توصية المنتج (Pharmacy/Labs)

**MVP:**
1. **فصل labs عن pharmacy** (قطاع/نوع عمل مستقل) أو تشغيل BookingPanel للمختبر (توسيع البوّابة المقيّدة {services,healthcare,realEstate}).
2. **رفع وصفة** (حقل على المنتج requires_prescription + رفع ملف قبل الإتمام) + **علامة controlled** تمنع البيع.
3. **تنويه/إخلاء مسؤوليّة طبّي إلزامي** + إلزام verification الترخيص.

**Phase 2 (مختبر):** كتالوج فحوصات/حزم + fasting flag + زيارة منزليّة (+رسوم) + سلوتات (provider_availability موجود) + حالات العيّنة/النتيجة + تذكير الصيام.

**Phase 3:** تسليم النتائج الرقمي الآمن + سجلّ فحوصات العميل + طلب متكرّر للأدوية المزمنة + تكامل مع «صحة وعيادات» (وصفة الطبيب → صيدليّة).
